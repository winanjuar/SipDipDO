# snd-dash - Epic Breakdown

> Dokumen ini di-shard per-epic: story lengkap masing-masing epic ada di `epic-1.md` … `epic-6.md` di folder ini; file ini memuat inventaris requirements, FR Coverage Map, dan Epic List sebagai peta navigasi.

## Overview

Dokumen ini memuat breakdown epic dan story lengkap untuk **snd-dash** (Sip & Dip Ownership Dashboard — Phase 1), hasil dekomposisi requirements dari PRD, kontrak UX (DESIGN.md + EXPERIENCE.md), dan Architecture Spine menjadi story yang dapat diimplementasikan.

## Requirements Inventory

### Functional Requirements

- **FR-1**: Pesanan Pembelian mandiri dengan validasi Strength — pratinjau hitungan (proyeksi Ceil, Shares, Strength, RTL) sebelum submit; harga berlaku tanggal submit menjadi Harga Terkunci; sistem menolak pesanan yang membuat Strength owner > 100% dengan pesan berisi hitungannya; validasi menggabungkan posisi terkini + seluruh pesanan owner berstatus Menunggu Konfirmasi; pilihan jenis modal mengikuti ketersediaan ruang RKAP; Quantity maksimal Modal Tetap/Bergerak = pembulatan ke atas sisa ruang ÷ harga (ceil) selama tertampung batas penyesuaian instant fase, bila batas habis mengikuti Quantity Left.
- **FR-2** `[Phase 2]`: Penjualan saham dengan harga jual berbeda — **di luar scope Phase 1**; dicantumkan untuk ketertelusuran.
- **FR-3**: MFA untuk aksi transaksional COO — konfirmasi Pesanan Pembelian dan input transaksi langsung wajib OTP via email sebelum efektif; submit pesanan owner tanpa MFA (Phase 1); permintaan MFA tercatat audit trail.
- **FR-4**: Tabel kepemilikan per owner — kolom Quantity, Shares, Portion, Ceil, Strength, Actual, RTL + Grand Total; Portion 2 desimal; owner baru muncul otomatis setelah transaksi pertama; RTL 0 = Strength optimal.
- **FR-5**: Visualisasi komposisi kepemilikan — chart Portion per owner yang otomatis menambah label owner baru; selalu sinkron dengan tabel (25 → ~40 owner).
- **FR-6**: CMS harga saham — COO mengelola harga beli & jual (nilai baru efektif per tanggal, tertaut MoM MRO); harga berjalan selalu tampil; riwayat lengkap; transaksi berikutnya otomatis memakai harga berlaku; harga terlihat semua owner termasuk tanpa saham.
- **FR-7**: Pencatatan MoM MRO/RUPS — dua modus: (a) **tulis langsung** di sistem: notulen draft → final, tersimpan dengan tanggal, dapat ditautkan ke keputusan (harga, jenis Contribution, cut-off); (b) **upload dokumen matang**: MoM yang disusun di text editor apa pun, hasil PDF-nya diupload COO ke sistem dan dapat **dipreview di web** oleh pemegang saham.
- **FR-8**: Definisi item Contribution — nama, deskripsi, poin kuantitatif, periode berlaku; tertaut MoM penetapan.
- **FR-9**: Pencatatan realisasi Contribution per owner oleh COO pada item terdefinisi; poin berjalan tampil untuk owner login dan rekap COO; setiap pencatatan bertanggal + pencatat.
- **FR-10**: Cut-off Contribution Period dengan carry-over — COO memicu cut-off pada tanggal tertentu; Contribution memenuhi syarat difinalkan sebagai dasar Insentif dan ditandai selesai; sisanya carry-over ke periode berikutnya; yang sudah diberi insentif tidak pernah muncul lagi.
- **FR-11**: Generate & kirim Bukti Transaksi — per transaksi efektif (konfirmasi maupun input langsung), berisi identitas owner, tanggal, jenis modal, Quantity, harga, Shares, Ceil, Strength, Portion setelah transaksi; dikirim via email (Template Konfirmasi Pembelian Saham v3); dapat diunduh ulang kapan pun.
- **FR-12**: Audit trail permanen — semua aksi (submit/tarik/kedaluwarsa/konfirmasi/tolak pesanan, input langsung, penetapan harga, cut-off, perubahan data dasar) tercatat aktor + waktu + detail; tidak dapat diubah/dihapus; hanya dapat dilihat COO; penolakan tercatat lengkap dengan alasan dan hitungannya.
- **FR-13**: Manajemen data owner — COO menambah/mengelola data owner (identitas, kontak WA/email, status); dapat memilih owner mana pun saat input transaksi; status owner: pemegang saham / tanpa saham (belum pernah beli / bekas pemegang) / Keluar; owner Keluar dapat aktif kembali (reaktivasi) dengan ruang RKAP tersedia.
- **FR-14**: Migrasi data historis — seluruh riwayat transaksi (termasuk sheet Evidence), rekap kepemilikan Google Sheets, data pendaftaran Google Form, **serta poin Contribution historis yang belum ditunaikan (delta atas PRD — keputusan user Step 3)** dimigrasikan; go-live dengan saldo & riwayat utuh 22 owner; Grand Total paritas: Quantity 3.622, Shares 5.187, Ceil 14.980; setiap owner dapat melihat riwayatnya pasca-migrasi.
- **FR-15**: Role dan hak akses — tiga tingkat: Calon Owner terverifikasi (hanya halaman personal), Owner pemegang saham (lihat dashboard/Contribution/Bukti sendiri; buat & tarik pesanan sendiri), COO (konfirmasi + input langsung dengan MFA; kelola konten & data dasar); transaksi hanya efektif via COO; matriks keterbukaan owner tanpa saham (terbuka: profile & pesanan sendiri, harga, RKAP, rekap selama punya poin belum ditunaikan; terkunci: tabel/chart kepemilikan, Contribution, MoM, audit); terkunci terbuka otomatis setelah Pembelian Pertama efektif.
- **FR-16**: Simulasi & rekap distribusi laba — COO input laba diaudit & laba ditahan; Laba Dibagikan dibagi ke Charity, Dividen (per Portion), Insentif (per Contribution) dengan ratio parameter RUPS; budget pool per komponen = ratio × Laba Dibagikan; Dividen owner = Portion × pool Dividen; Insentif owner = (poin ÷ total poin) × pool Insentif; basis poin = periode ter-finalkan cut-off; owner tanpa saham yang Insentif-nya ditunaikan pada rekap → status Keluar; rekap bisa dibandingkan dengan rekap sebelumnya; terlihat sesuai matriks keterbukaan.
- **FR-17**: Pergantian COO — peran dapat dialihkan ke owner lain (keputusan MRO/RUPS, wajib referensi MoM); riwayat tenure tercatat audit trail; COO lama otomatis kembali Owner biasa; transaksi tercatat atas nama pejabat saat itu.
- **FR-18**: Chart-chart dashboard paritas spreadsheet — (1) Pie "Portion Kepemilikan" (label nama + persentase); (2) Donut dua cincin "Distribusi Pemodalan" (cincin dalam per jenis modal, luar per owner); (3) Stacked bar "Big Cap" (Shares vs Ceil per kelompok kap; agregat `[Medium Cap]`/`[Small Cap]`); ambang Big > 5%, Medium > 2%, Small ≤ 2% — data konfigurasi; kelompok dihitung ulang otomatis dari Portion terkini; selalu sinkron dengan tabel.
- **FR-19**: Antrian Beli & siklus hidup pesanan — status 4-state (Menunggu Konfirmasi, Terkonfirmasi, Ditolak, Kedaluwarsa); penarikan oleh owner hanya saat Menunggu Konfirmasi (bukan status — keluar antrian, tercatat audit); kedaluwarsa otomatis hari ke-7 sejak submit; Antrian Beli lengkap hanya COO, owner hanya pesanannya sendiri; notifikasi email ke COO per pesanan baru.
- **FR-20**: Konfirmasi COO dengan re-validasi & pencatatan pembayaran — COO mengisi tanggal + metode transfer (tanpa upload bukti), plotting alokasi ke Capital Item (default FIFO), konfirmasi dengan MFA; sistem re-validasi aturan pembelian memakai kondisi terkini (Strength, ruang RKAP, keabsahan referral Pembelian Pertama); harga final tetap Harga Terkunci; gagal re-validasi → Ditolak + penjelasan hitungan + saran pengalihan/refund; efektif → Fulfillment RKAP tercetak, dashboard/rekap/chart terupdate, Bukti terkirim.
- **FR-21**: Jalur input langsung COO — catat pembelian langsung atas nama owner (mis. tunai di cafe); validasi Strength sama seperti FR-1; harga berjalan tanggal input; pencatatan pembayaran + MFA; langsung efektif tanpa melewati Antrian Beli; tercatat audit sebagai input langsung; Pembelian Pertama via jalur ini juga wajib referral.
- **FR-22**: Pendaftaran owner mandiri — daftar dengan akun Google (link publik, tanpa syarat referral); lengkapi Profile 11 field Lampiran A (prasyarat verifikasi); verifikasi/penolakan COO tercatat audit; status Diajukan/Terverifikasi/Ditolak; pengingat email + kedaluwarsa otomatis 7 hari untuk Profile belum lengkap (bisa daftar ulang); referral diajukan saat Pembelian Pertama (pilihan: pemegang saham atau owner belum pernah beli; cross-referral hari sama divalidasi COO); owner tanpa saham hanya halaman personal; autentikasi semua akun via Google, dicocokkan email saat migrasi.
- **FR-23**: Pencatatan & pelacakan RKAP — tabel Capital Item per fase (nama, jenis modal Tetap/Bergerak, Initial Requirement, Final Requirement, Fulfillment, Fulfillment Rate, Shortfall, Utilization, Achievement, Held) + agregat ruang per jenis modal; Initial dikunci saat MRO; Final hanya bergerak via penyesuaian instant otomatis (overshoot pembulatan) maupun manual COO (kenaikan item / item baru); batas penyesuaian agregat per fase = (1% × total Initial) + harga 1 saham berjalan; Fulfillment hanya dari transaksi efektif (antrian tidak memesan ruang); gerbang per jenis modal tutup saat Fulfillment Rate 100%; Utilization diinput COO (Achievement bisa > 100%, Held = Fulfillment − Utilization); rebalancing antar item sejenis tertaut MoM; setiap perubahan tercatat audit; plotting alokasi ditetapkan COO saat validasi (default FIFO); tampil sebagai tabel tersendiri terlihat semua owner termasuk tanpa saham + ringkasan batas + Quantity Left.

### NonFunctional Requirements

- **NFR-1**: Presisi perhitungan pecahan lintas-fitur — 2 angka di belakang koma, pembulatan half-up (≥5 ke atas); total Portion ditampilkan apa adanya meski 99,99%/100,01%.
- **NFR-2** (SM-1): Zero discrepancy — tidak ada temuan selisih hitungan Portion antara sistem dan verifikasi manual owner selama 3 bulan pasca go-live (gerbang migrasi & perhitungan).
- **NFR-3** (SM-2): Google Sheets berhenti dipakai untuk pencatatan saham dalam 1 bulan pasca go-live.
- **NFR-4** (SM-3): 100% transaksi baru menghasilkan Bukti Transaksi terkirim ke owner terkait.
- **NFR-5** (SM-4): COO menyelesaikan konfirmasi satu pesanan (pencatatan pembayaran + re-validasi + MFA) < 5 menit.
- **NFR-6**: Web app responsif untuk 22 owner eksisting → pertumbuhan ~40; mobile-browser-first untuk owner, desktop-capable untuk alur berat COO; breakpoint tunggal `lg` (1024px).

Bentuk internal modul seragam: `index.ts` satu-satunya pintu impor lintas modul, `*.service.ts` kasus penggunaan, `*.repo.ts` satu-satunya tempat Drizzle, `events.ts` opsional. Tidak ada starter template siap pakai — scaffold dari awal dengan pin stack (Epic 1 Story 1).

- **AR-3 — Smoke-test wajib saat scaffold**: (1) NuxtAuth OAuth Google + session di Nuxt 4 (fallback: `nuxt-auth-utils` / OAuth manual — tetap memenuhi AD-8); (2) `@vite-pwa/nuxt` BUILD (generateSW) + install + prompt pembaruan di Nuxt 4.5 (fallback: `vite-plugin-pwa` langsung / SW kustom direviu terhadap AD-12); (3) paritas komponen kontrak shadcn-vue (Dialog/Sheet/Tooltip/Drawer/Input-OTP/Toast).
- **AR-4 — Invariant arsitektur AD-1..AD-12 mengikat seluruh implementasi**: ledger append-only + entry kompensasi (AD-1); finalisasi atomik satu transaksi DB + compare-and-set + urutan lock global `buy_orders → rkap_phases → positions → owners → contribution_periods → distribution` + guard `withdrawn_at IS NULL` (AD-2); audit in-tx append-only (AD-3); posisi tabel proyeksi terkopling atomik dengan ledger (AD-4); kepemilikan tabel mutlak per modul + OTP verify/konsumsi in-tx (AD-5, AD-8); satu implementasi rumus di `shared/domain` + fungsi assembly kanonik per gerbang (AD-6); Harga Terkunci snapshot + `price_periods` unique per (jenis harga, tanggal efektif) (AD-7); akses tiga tingkat dipaksa di batas server + himpunan tertutup aksi ber-MFA + OTP terikat `{action_type, target_ref}` (AD-8); Vercel + Supabase + cron dengan batas hari Asia/Jakarta (AD-9); uang `numeric(18,2)` + kontrak kawat string desimal + decimal library tunggal (AD-10); siklus hidup owner satu penulis + CAS (AD-11); PWA cangkang + `no-store` + kontrak kesegaran runtime (AD-12).
- **AR-5 — PWA installable level A**: manifest `display: standalone` tanpa `orientation`; cache hanya aset build ter-fingerprint + manifest + ikon + `/offline`; dokumen SSR & `/api/**` `Cache-Control: no-store`; tanpa `swr`/`isr` rute domain; `registerType: 'prompt'` tanpa `skipWaiting`; prompt pembaruan tidak di atas dialog transaksional.
- **AR-6 — Email via pola outbox**: baris outbox ditulis dalam transaksi aksi terkait; pengiriman async + retry oleh modul PROOFS; kegagalan kirim tidak membatalkan transaksi; Resend + SPF/DKIM + From-domain ditetapkan saat scaffold; retry outbox yang terus gagal wajib terlihat (log + alert), bukan kegagalan senyap.
- **AR-7 — Vercel Cron terproteksi**: endpoint cron harian (UTC) memakai CRON_SECRET; job: kedaluwarsa pesanan hari-7 (FR-19) + pengingat/kedaluwarsa pendaftar (FR-22); batas hari dihitung di dalam endpoint memakai zona Asia/Jakarta, bukan jam trigger UTC.
- **AR-8 — Migrasi via pintu finalisasi LEDGER lengkap**: import memakai API internal LEDGER sesuai isi AD-2 (termasuk plotting alokasi per Capital Item direkonstruksi dari kolom Pemenuhan spreadsheet + pencatatan pembayaran historis, metode `'migrasi'` bila tak diketahui) TANPA re-validasi gerbang domain dan TANPA baris outbox email untuk transaksi berlabel migrasi (Bukti hanya regenerate-on-demand); `price_periods` historis berlabel migrasi (FK harga tidak pernah null); aktor `system`; acceptance mencakup paritas Fulfillment Rate per jenis modal + Grand Total.
- **AR-9 — Kontrak data & penamaan**: ID `uuid`; tanggal `timestamptz` UTC; seluruh aturan kalender-hari dihitung zona Asia/Jakarta; uang `numeric(18,2)`, ratio `numeric(9,6)` presisi penuh + half-up 2 desimal saat penyajian; bentuk error API seragam `{ code, message, details }`; enum dipinkan (status pesanan 4-state; status owner/pendaftaran `diajukan`/`terverifikasi`/`ditolak`/`kedaluwarsa`/`keluar`); istilah Glossary PRD verbatim di UI dan identifier; tabel DB snake_case jamak; komponen Vue PascalCase; file TS kebab-case.

- **AR-11 — Operasional**: lingkungan `local` + `production` saja; pengembangan lokal via Supabase CLI (Docker); backup Supabase harian/PITR aktif + satu drill restore terdokumentasi sebelum go-live; log terstruktur; konfigurasi via env.
- **AR-12 — Keputusan scaffold tertunda**: library chart (FR-18; kebutuhan donut dua cincin memiringkan ke ECharts) dan decimal library dipin saat scaffold — bukan story terpisah, tetapi risiko yang harus dieksekusi eksplisit.
- **AR-13 — File storage MoM PDF (delta atas spine, keputusan user Step 1)**: upload PDF MoM (FR-7 modus b) memerlukan object storage — Supabase Storage bucket privat (konsisten platform AD-9), akses terautentikasi sesuai keterbukaan MoM (pemegang saham + COO); preview via viewer browser dengan URL berumur pendek; spine belum mengatur file storage — Bukti Transaksi tetap regenerasi deterministik (AD/State konvensi), tidak terdampak.
